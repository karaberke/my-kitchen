# sections.md — code map for incremental simplification

Purpose: an agent picks **one section at a time** and simplifies it without
breaking the rest. Each section lists its files, how it works (the pipeline),
what it depends on and what depends on it, and concrete simplification
suggestions. Line counts were measured once; re-measure with `wc -l` before
starting work.

## Stack

One SvelteKit 2 application (Svelte 5 runes, Tailwind 4, adapter-node), one
PostgreSQL 17 database through Drizzle ORM, Better Auth for accounts. All
quantity arithmetic uses `Dec` (BigInt, six decimals) mirroring the
`numeric(14,6)` columns; `Dec` crosses JSON as a string; `null` means unknown
and is **not** zero.

## Layer rules (from AGENTS.md / CLAUDE.md)

- `src/lib/server/` — server-only (database, access control, domain ops).
- `src/lib/shared/` — pure logic, runs on both sides.
- `src/lib/client/` — browser-only.
- Routes hold no domain logic: a `+page.server.ts` parses the form, calls a
  function in `src/lib/server/`, and maps the error.
- `event.locals` (filled once per request by `hooks.server.ts`) is a cache,
  not an authority — every load and action re-checks membership against the
  database.

## Universal invariants (must survive any simplification)

1. **Writes** go through `withTransaction` / `runOperation` in
   `src/lib/server/operations.ts`: claim the client-supplied operation id with
   a payload fingerprint (idempotency), lock the household row **first**, then
   the lots by id, write the event plus append-only `inventory_movement` rows,
   retry on serialization failure. Undo is a compensating event, not a delete.
2. **Access control**: every load/action calls `requireUser` /
   `requireHousehold` from `src/lib/server/access.ts` and then
   `assertMember(db, householdId, userId)` against the DB — again inside the
   transaction for a write.
3. **Freshness**: `household.pantry_revision`, `grocery_revision` and
   `plan_revision` change in the same transaction as the data (via
   `lockHousehold` in `src/lib/server/inventory.ts`), and the client polls
   `/api/revisions`. Bump the correct counter or screens stop refreshing.
4. **Schema**: changes need `pnpm db:generate`; `drizzle/` is generated and
   applied by `scripts/migrate.mjs`, never `drizzle-kit push`.
5. **Definition of done**: `pnpm check`, `pnpm lint`, `pnpm test` pass; new
   behavior has a test that fails without the change.

## 1. Request lifecycle & app shell

**Files**

- `src/hooks.server.ts` (96) — session resolution, response policy, `init()`
- `src/app.d.ts` (32) — `App.Locals` shape
- `src/params/uuid.ts` (11) — route param guard
- `src/routes/+layout.svelte` (33), `+layout.server.ts` (17), `+error.svelte`,
  `layout.css`
- `svelte.config.js` — the **Content-Security-Policy lives here**; a new
  external origin needs a directive there as well

**How it works.** `handleSession` runs once per request: sets
`event.locals.requestId`, resolves the Better Auth session, loads `memberships`
and the active `household` into `event.locals` (no module-level user state
exists anywhere on the server). It 404s Better Auth's own
`/api/auth/sign-up` endpoint (accounts are created only by the `/register`
action or the `ADMIN_*` bootstrap — a documented security decision, keep it).
Every response is wrapped in `applyResponsePolicy` (default `private,
no-store`; a route opts out explicitly). `init()` runs `ensureAdminAccount`
and starts an unref'd hourly sweep calling `cleanupUnreferencedImages`,
`cleanupUnreferencedAttachments`, `cleanupOperations` and
`cleanupBarcodeCache`.

**Depends on.** Section 3 (access, auth, env), section 4
(`cleanupOperations`), section 8 (`cleanupBarcodeCache`), section 9 (media
cleanups).
**Used by.** Everything — it is the entry point.

**Simplification suggestions.**

- The hourly sweep couples the hook to four unrelated modules. Collect the
  four cleanup functions in one `src/lib/server/housekeeping.ts` that the
  hook calls — the hook shrinks and the interval/sweep logic becomes
  testable in isolation.
- `applyResponsePolicy` is defined in `src/lib/server/http.ts` and called
  from the hook (and `csp.test.ts`). Keep it in `http.ts`; do not move it
  into the hook.

**Guarded by.** `src/lib/server/csp.test.ts`; e2e `caching.spec.ts`,
`sync.spec.ts`, `household.spec.ts`.

## 2. Database & schema

**Files**

- `src/lib/server/db/schema.ts` (758) — all 23 Drizzle tables
- `src/lib/server/db/index.ts` (29) — `db`, `Db`, `Tx`, `DbOrTx`, `closeDb`
- `src/lib/server/db/auth.schema.ts` — Better Auth tables (regenerated by
  `pnpm auth:schema` after a Better Auth config change)
- `src/lib/server/db/ssl.ts` (+ `ssl.test.ts`) — `sslOptions` for the pool
- `drizzle/` — **generated, do not edit by hand**
- `scripts/migrate.mjs` (70) — applies migrations

**How it works.** Tables group by domain: household (3), user_preference,
ingredient (2), image / recipe_attachment (2), recipe (6), stock_lot /
operation, grocery (5: list, batch, batch_requirement, line, line_source),
inventory_event / inventory_movement / purchase_allocation, meal_plan_entry,
barcode (5: product, product_nutrient, miss, link, …). Every other module
imports the `db` instance and the `DbOrTx` type from `db/index.ts`; queries
import table objects directly from `db/schema`.

**Depends on.** Section 3 (`env.ts` supplies `DATABASE_URL`, `ssl.ts`).
**Used by.** Every section — this is the bottom of the dependency graph.

**Simplification suggestions.**

- Split `schema.ts` (758 lines) into per-domain files (`household.ts`,
  `recipe.ts`, `grocery.ts`, `inventory.ts`, `barcode.ts`, `media.ts`)
  re-exported from one `schema.ts` index. This is a pure file move (no DDL
  change); run `pnpm db:generate` afterwards to confirm zero drift.
- Keep table names, column types and constraint names stable — the
  `operation_pkey` unique violation is checked **by name** in
  `operations.ts` (`isUniqueViolation(err, 'operation_pkey')`).

**Guarded by.** the whole integration suite; `pnpm db:check`
(`scripts/consistency-check.mjs`).

**Depends on.** Section 2, `env.ts`.

  `removeMember`, `setMemberRole`, `deleteHousehold`). Split reads from
  writes; be careful with `deleteHousehold` — it is covered by
  `integration/delete-household.test.ts`.

**Guarded by.** `integration/accounts.test.ts`, `access.test.ts`,
`delete-household.test.ts`, `social-signup.test.ts`; e2e `household.spec.ts`.

## 4. Mutation kernel: transactions, idempotency, events, lots

**Files**

- `src/lib/server/operations.ts` (146) — `stableStringify`, `fingerprint`,
  `withTransaction` (retries SQLSTATE 40001/40P01, 3 attempts, backoff),
  `runOperation` (exactly-once: op-id claimed inside the tx, replay on
  identical payload, 409 on id reuse with a different payload),
  `cleanupOperations`
- `src/lib/server/inventory.ts` (340) — `lockHousehold` (SELECT ... FOR
  UPDATE + bumps `pantry/grocery/plan` revisions per the flags passed),
  `lockLots`, `insertEvent`, `applyMovement` (balance guard on the lot),
  `createLot`, pure `planDeduction`, `activeLotsForIngredients`
- `src/lib/server/undo.ts` (185) — `undoEvent`: a compensating event that
  reverses the movements of an earlier event
- `src/routes/api/revisions/+server.ts` — the polling target
  (`{ pantry, grocery, plan }` counters)

**How it works.** The core write pipeline used by every mutation in the app:
a route supplies an `operationId` (`randomUUID()` in the load, or
`newOperationId()` from `src/lib/client/ids.ts` in the browser) →
`runOperation` inserts the `operations` row **inside** the transaction
(concurrent retries block on the primary key, then replay or 409) →
`lockHousehold` (bumps revision counters) → `lockLots` → `insertEvent` +
`applyMovement` / `createLot` → commit. Serialization failures and deadlocks
retry with jittered backoff.

**Depends on.** Section 2, `errors.ts`.
**Used by.** Sections 5–8 — `withTransaction` has 8 call sites across
`grocery.ts`, `pantry.ts`, `cooking.ts`, `plan.ts`, `recipes.ts`,
`households.ts`, `ingredient-links.ts`, `barcode/lookup.ts`.

**Simplification suggestions.**

- `const { pantryRevision } = await lockHousehold(tx, ctx.householdId, {…})`
  appears ~15× across sections 5–8, always followed by event writes. A small
  per-domain wrapper around `runOperation` (receiving the bump flags and an
  `effect(tx)` callback) would remove the repetition — **but keep the lock
  order (household first, then lots by id)** or the concurrency tests break.
- `stableStringify` is the only hand-rolled JSON normalization in the repo;
  keep it — it is what makes the operation fingerprints stable.
- `planDeduction` is pure (no DB) but lives in `inventory.ts` because
  cooking/grocery need it next to `activeLotsForIngredients`; moving it to
  `shared/` would require feeding it `Dec` values both sides already have —
  a reasonable later move, low urgency.

**Guarded by.** `integration/concurrency.test.ts`, `cooking-undo.test.ts`,
`grocery-flow.test.ts`, `remediation.test.ts`, `plan.test.ts`.

## 5. Pantry & cooking

**Files**

- `src/lib/server/pantry.ts` (705) — `getPantryOverview` (groups,
  `USE_SOON_DAYS = 7`), `getLot`, `addStock`, `updateLotMetadata`,
  `correctLot`, `wasteLot`, cursor-based `getHistory`, `consistencyCheck`
  (backs `pnpm db:check`)
- `src/lib/server/cooking.ts` (497) — `previewCooking` (pure read:
  `activeLotsForIngredients` + `planDeduction` per ingredient),
  `finishCooking` (events + per-lot `applyMovement`; bumps pantry **and**
  grocery when a line ends up short), `lotsForIngredient`
- `src/routes/(app)/pantry/*` (page 549 + server 236; `history/` page 122),
  `src/routes/(app)/recipes/[id=uuid]/cook/*` (page 468 + server 131)
- `src/routes/api/pantry-lots/+server.ts`

**How it works (scan → stock).** `BarcodeScanner.svelte` decodes camera
frames (section 8) → `GET /api/barcode` → `suggestionFor` →
`ScanConfirm.svelte` → `POST addStock` → section 4 (`createLot` +
`insertEvent` + revision bump). Corrections, metadata edits and waste are the
same pipeline with different event kinds. Undo works from the pantry and
history screens via `undoEvent`. Cooking: the cook page previews deductions
read-only; `finishCooking` consumes lots and, for what is missing, writes
grocery requirement rows — which is why it bumps both the pantry and the
grocery counter.

**Depends on.** Section 4, section 8 (barcode lookup, ingredient links),
`shared/units`, `shared/decimal`, `shared/stock-status`.
**Used by.** Section 6 (grocery reads stock and snapshots
`pantryRevisionAtPreview`), section 11 (screens), section 1 (history undo
links).

**Simplification suggestions.**

- `addStock` / `updateLotMetadata` / `correctLot` / `wasteLot` are four
  near-identical bodies: `runOperation` → `lockHousehold` → lot update →
  `insertEvent` / `applyMovement` → revision bump. Extract one
  `mutateLot(ctx, kind, effect)` helper that takes the differing part as a
  callback.
- `consistencyCheck` in `pantry.ts` and `scripts/consistency-check.mjs`
  (raw `postgres` via `db-ssl.mjs`) implement the same checks twice. Keep
  one source of truth (the server function) and have the script call it, or
  at minimum keep the two rule lists deliberately in sync.
- `getHistory` cursor decoding and `getPantryOverview` grouping are the only
  genuinely query-heavy parts; the mutation bodies are boilerplate.

**Guarded by.** `integration/cooking-undo.test.ts` (305 lines),
`concurrency.test.ts`, `grocery-flow.test.ts` (stock side); e2e
`shopping.spec.ts`, `upload.spec.ts`, `sync.spec.ts`.

## 6. Grocery & meal plan

**Files**

- `src/lib/server/grocery.ts` (1293) — **largest file in the repo**: list
  CRUD, `getListDetail` (batch + line views), `recalculateDraft` (calls the
  shared pure `computePlan`), `addBatch` / `updateBatch` / `removeBatch` (a
  batch is a recipe or a manual requirement set), `refreshDraft`, manual
  lines, `startShopping`, `recordPurchase` (writes `purchase_allocations`
  and restocks via `createLot`), `completeList` / `reopenList`
- `src/lib/server/plan.ts` (181) — `PLAN_DAYS = 7`, `mondayOf`, `weekDates`,
  `getWeekPlan`, `addPlanEntry` / `removePlanEntry`, `planWeekToGrocery`
- `src/lib/shared/grocery-math.ts` (307) — pure `computePlan`
  (requirements vs stock → missing amounts), `remainingTarget`
- `src/lib/shared/scaling.ts` (17) — servings scaling for batch quantities
- `src/routes/(app)/grocery/*` (list page 56 + server 56; detail 695 +
  server 251), `src/routes/(app)/plan/*` (page 204 + server 89)

**How it works.** The grocery state machine: a list starts as `draft`.
Entries come from the meal plan (`planWeekToGrocery`) or manually
(`addBatch` / manual lines). `recalculateDraft` runs the shared pure
`computePlan` against current stock and snapshots
`pantryRevisionAtPreview` so the draft knows which stock it was computed
against. `startShopping` flips draft → shopping. `recordPurchase` writes
`purchase_allocations` rows (which purchase covered which line) and
restocks the pantry through section 4 (`createLot`). `completeList` /
`reopenList` close the cycle. The plan side is read-heavy: `getWeekPlan`
plus two small mutations.

**Depends on.** Section 4 (heaviest user — ~8 `lockHousehold` call sites),
`shared/grocery-math`, `shared/decimal`, `shared/units`, `shared/time`,
`server/ingredients` (names/categories).
**Used by.** Section 5 (`finishCooking` writes missing-line requirements
here), section 11 (screens), section 1 (`/api/revisions` polling drives the
detail page via `PollRevisions.svelte`).

**Simplification suggestions.**

- Split the 1293-line file into three sub-domains that are currently
  interleaved: `grocery-lists.ts` (list CRUD + views), `grocery-draft.ts`
  (recalculation, batch/line editing, `pantryRevisionAtPreview` handling),
  `grocery-shopping.ts` (state machine + purchases + allocations). The
  shared view types (`BatchView`, `LineView`, `ListDetail`) should travel
  with the queries that build them.
- The `const { pantryRevision } = await lockHousehold(...)` pattern repeats
  ~8× inside this file alone — a local wrapper (or the section-4
  `runOperation` wrapper) collapses it.
- `shared/grocery-math.ts` is already pure and well-tested (370 lines of
  tests); do not move logic out of it into the server files — the direction
  of refactor is server boilerplate in, math out.

**Guarded by.** `integration/grocery-flow.test.ts` (468), `plan.test.ts`
(183); `shared/grocery-math.test.ts` (370); e2e `shopping.spec.ts`,
`plan.spec.ts`, `sync.spec.ts`.

- The import route's server load (207 lines) orchestrates parse + match +
  prefilled form; most of it is glue — the real work is already in the

**Guarded by.** `integration/recipes.test.ts` (362),

**How it works (scan pipeline).** Camera frame → `decodeFrame`

`BARCODE_LIMITS`) → `lookupBarcode`: cache read → USDA → Open Food Facts,

**Depends on.** Section 4 (cache writes run in a transaction),

- The 447-line `lookup.ts` mixes cache reads, provider orchestration, the

  the product + ingredient rows and is the natural candidate to move to
  `shared/` (it needs no server-only imports); the cache + orchestration
  stays.
- `shared/gtin.ts` is already the single identity source for both sides;
  keep it that way when refactoring the barcode adapters.

**Guarded by.** `server/barcode/usda.test.ts` (205) and `off.test.ts` (174)

`ingredient-match.test.ts`, `ingredient-links.test.ts` (113);
`shared/gtin.test.ts` (142); e2e `barcode.spec.ts` (252).

## 9. Media & file storage

**Files**

- `src/lib/server/media/storage.ts` (138) — `StorageAdapter` (local disk or
  S3), `assertKey` path guard
- `src/lib/server/media/images.ts` (190) — `storeRecipeImage`,
  `storeRecipeImageFromUrl`, `loadReadableImage` (ownership check),
  variant keys
- `src/lib/server/media/image-pipeline.ts` (99) — `IMAGE_VARIANTS`,
  `renderImageVariants`
- `src/lib/server/media/image-fetch.ts` (125) — remote fetch with size
  limit (import-by-URL path)
- `src/lib/server/media/attachments.ts` (124) — 10MB limit,
  `attachToRecipe`, cleanup
- `src/lib/server/media/pdf.ts` (30) — `extractPdfText` (import path)
- `src/lib/client/image-resize.ts` — downscale before upload
- `src/routes/media/[imageId]/[variant]/+server.ts`,
  `routes/media/attachment/[attachmentId]/+server.ts` — access is checked
  **before** answering, including before a 304

**How it works.** Browser resize → store → variants rendered on write →
route serves a variant after checking access. Recipes reference images and
attachments by row; the hourly sweep (section 1) deletes rows that no recipe
references.

**Depends on.** Section 2, section 3 (access checks, `env.ts` for S3
credentials), section 7 (the only producer of uploads besides attachments).
**Used by.** Section 7 (recipe images, attachments, PDF import), section 1
(sweeps).

**Simplification suggestions.**

- Images and attachments repeat the same store → render/validate → serve →
  cleanup shape. The adapter already abstracts storage; a single
  `storeObject` / `loadObject` pair could serve both and cut the duplicated
  key-building, size-limit and access-check glue (~150 lines).
- `image-fetch.ts` (remote fetch) is used only by the import path
